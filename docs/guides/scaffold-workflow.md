# Scaffold workflow

This guide explains how to keep an initialized application repository synchronized with later versions of the BU-ISCIII deployment standard without losing changes made at supported extension points. For initial generation, see [Creating a project](creating-a-project.md).

## 1. Overview

The scaffold is both a generator and a synchronization tool. It records the generated baseline during `init`, reports differences with `check`, applies compatible changes with `sync`, and manages the shared deployment library with `check-lib` and `sync-lib`.

This guide covers the normal maintenance workflow rather than every command-line option.

## 2. Scaffold state

The scaffold stores its state in:

```text
.bu-isciii-deployment/state.json
```

This file records the project descriptor and checksums for generated files. `check` and `sync` use it to distinguish a central standard update from a local change to managed content.

The state file is part of the generated deployment baseline and should normally be committed. Do not edit it manually; let `init` and `sync` maintain it.

## 3. Check the current repository

Run the read-only check from an up-to-date checkout of the standards repository:

```bash
python3 /path/to/buisciii-deployment-standards/scripts/scaffold.py \
  check /path/to/application
```

`check` does not modify the application repository. It exits with a non-zero status if it finds a synchronization issue.

| Status | Meaning |
| --- | --- |
| `current` | The file matches the standard or differs only within its allowed application-owned contract. |
| `update-available` | The central standard changed and `sync` can apply the change safely. |
| `managed-drift-without-update` | Standard-managed content was changed locally, but the central version has not changed. |
| `managed-drift-with-update` | Standard-managed content changed both locally and in the central standard. |
| `contract-drift` | A structured file violates its required schema or structural contract and needs manual repair. |
| `missing` | An expected generated file does not exist. |
| `obsolete` | A path recorded by the previous baseline is no longer generated by the current descriptor and standard. |

The same check also reports shared library paths as `current`, `missing`, or `modified`.

## 4. Synchronize generated files

Apply compatible scaffold changes with:

```bash
python3 /path/to/buisciii-deployment-standards/scripts/scaffold.py \
  sync /path/to/application
```

`sync` updates unmodified generated files, creates missing generated files, and preserves content inside declared application-owned blocks. Schema-managed configuration keeps existing values and application-only variables while adding missing standard variable names. It does not blindly regenerate the repository.

If standard-managed content was edited locally, `sync` leaves the local file unchanged and writes the current generated version beside it with the suffix `.bu-isciii-update`. The command returns a non-zero status while such issues remain unresolved.

`sync` also synchronizes the centrally owned files under `deployment/lib/`.

## 5. Understand file ownership

Application-specific changes are safe only at declared extension points.

| Artifact | Ownership |
| --- | --- |
| `README.md`, `LEAME.md` | Standard-managed except for named application documentation blocks. |
| `container_install.sh` | Standard-managed except for the application deployment hooks block. |
| Django `install.sh` | Standard-managed except for the `install-hooks` block. |
| Compose files, `Dockerfile`, health implementation and smoke-test structure | Fully generated; change the descriptor or owning central template instead of editing generated content. |
| `conf/docker_*_settings.txt` and addon settings files | Variable names are standard-managed; local values and application-only variables are preserved. |
| `conf/template_settings.py` | Application-owned Django code checked against the renderer and structural contract. |
| `conf/urls.py` | Standard-managed health route with application-owned import and route blocks. |
| `deployment/lib/**` | Exact copies of the central shared library; never edit locally. |

Other profile and addon files may have more specific contracts. See [Generated project structure](../reference/generated-project-structure.md) and the generated documentation before editing them.

## 6. Resolve managed drift

When `sync` finds a local edit outside an application-owned block, it creates a candidate such as:

```text
README.md
README.md.bu-isciii-update
```

The original file contains the local managed change. The candidate contains the version produced by the current standard, with supported application-owned blocks preserved. Compare them:

```bash
diff -u README.md README.md.bu-isciii-update
```

Merge the intentional application content into a supported application-owned block or discard the unsupported managed edit. Make the real file match the required managed content, remove the candidate, and run `check` again. Candidate files are local synchronization artifacts and are ignored by the generated `.gitignore`.

## 7. Synchronize shared libraries

Check only the centrally owned deployment library with:

```bash
python3 /path/to/buisciii-deployment-standards/scripts/scaffold.py \
  check-lib /path/to/application
```

Replace missing or modified shared copies with the canonical implementation using:

```bash
python3 /path/to/buisciii-deployment-standards/scripts/scaffold.py \
  sync-lib /path/to/application
```

`check-lib` is read-only. `sync-lib` operates only below `deployment/lib/` and replaces drifted shared files.

Do not edit vendored files under `deployment/lib/` in the application repository. Application-specific behavior belongs in the provided hooks; reusable profile, addon, or common behavior belongs in its corresponding source template or central library.

## 8. Change the project descriptor

The initialized descriptor is stored in scaffold state, so normal `check` and `sync` commands can reuse it. To apply a supported descriptor change, pass the updated descriptor to `sync`:

```bash
python3 /path/to/buisciii-deployment-standards/scripts/scaffold.py \
  sync /path/to/application \
  --config /tmp/application.json
```

The scaffold accepts changes that keep the initialized deployment shape compatible. Multi-service projects can evolve their service and addon declarations through synchronization. Changing from a repository-owned profile to a multi-service-only shape, or changing the repository-owned framework profile, is rejected because it could mix incompatible generated artifacts. Initialize a new target for such a structural migration.

See [Project descriptor](../reference/project-descriptor.md) for descriptor fields and validation rules.

## 9. Recommended update workflow

1. Update the local checkout of `buisciii-deployment-standards` to the intended version.
2. Run `scaffold.py check`.
3. Review all reported updates and drift.
4. Run `scaffold.py sync`.
5. Resolve every `.bu-isciii-update` candidate.
6. Run `scaffold.py check` again.
7. Run the relevant application tests and generated smoke tests.
8. Review and commit the synchronized files and scaffold state.

For example:

```bash
git -C /path/to/buisciii-deployment-standards pull

python3 /path/to/buisciii-deployment-standards/scripts/scaffold.py \
  check /path/to/application

python3 /path/to/buisciii-deployment-standards/scripts/scaffold.py \
  sync /path/to/application
```

Review the selected standard revision before using `git pull` in a controlled deployment process.

## 10. Common situations

| Situation | Action |
| --- | --- |
| `update-available` | Run `sync`, then review the changed file. |
| `.bu-isciii-update` exists | Compare it with the real file, resolve the managed edit, remove the candidate, and rerun `check`. |
| A file under `deployment/lib/` is modified | Run `sync-lib` and move custom logic to an appropriate extension point. |
| A generated file is `missing` | Run `sync` and review the restored file. |
| `contract-drift` | Repair the reported schema or structural problem manually, then rerun `check`. |
| A descriptor change is rejected | Keep the existing deployment shape or initialize a separate target for the new structure. |

Passing `check` confirms scaffold synchronization only. It does not prove that the application satisfies every production, infrastructure, or security requirement. Continue with the [Deployment workflow](deployment-workflow.md) for deployment execution.
