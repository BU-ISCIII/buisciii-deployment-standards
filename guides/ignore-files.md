# Ignore files

Generated deployments use two ignore files for different boundaries:

> `.gitignore` protects the repository workflow.
> `.dockerignore` protects and reduces the image build context.

Neither file is a complete secret-management mechanism.

## Why there are two ignore files

`.gitignore` tells Git which untracked local files it should normally leave
alone. `.dockerignore` tells Docker or Podman which files to remove from the
build context.

A build context is the directory of files made available to the image builder.
A file ignored by Git can still enter that context unless `.dockerignore`
also excludes it.

For example, protected production settings are copied under
`deployment/settings/`. The generated templates exclude that directory from
both Git and the build context.

## `.gitignore`

The generated `.gitignore` excludes these categories:

- local Compose environment files, including `.env.*.file`;
- protected production copies under `deployment/settings/` and named legacy
  production-settings paths;
- rendered Apache files under `deployment/apache/`;
- scaffold synchronization candidates ending in `.bu-isciii-update`;
- Python bytecode and virtual environments;
- Node dependencies and Next.js/npm output;
- logs and local document storage.

These rules reduce accidental commits. They do not remove a file that Git
already tracks, and they do not review files added with an override. Check a
sensitive path before committing:

```bash
git status --ignored
git ls-files <path>
```

If `git ls-files` prints the path, the file is tracked regardless of an ignore
rule.

## `.dockerignore`

The generated `.dockerignore` excludes files that should not be available to
the builder, including:

- root-level installation settings matched by `conf/*settings*.txt`, except
  the explicitly re-included test and template settings;
- temporary installation-settings copies and local `.env` files, while
  allowing `.env.example`;
- protected settings under `deployment/settings/` and rendered Apache files;
- Python environments and caches;
- Node dependencies and npm, Next.js, and Vite caches;
- editor state, logs, temporary files, local documents, and common build output.

Keeping these files out of the build context has three effects: sensitive local
values do not reach the builder, less data is transferred, and local generated
files cannot silently change an otherwise repeatable build.

The current template does not contain a blanket `.git` exclusion or a generic
backup-file pattern. Do not assume that an unlisted file is excluded.

## Sensitive configuration

Real production values belong in protected, non-committed copies under
`deployment/settings/`, not in the generated `conf/` templates. The
standard excludes `deployment/settings/` from both Git and image builds.

The Django production build receives its selected settings through the
implemented build-secret interface. That transfer does not make arbitrary
files in the build context safe. Keep secrets out of normal build arguments,
source files, and generated frontend bundles.

See [Configuration](configuration.md) for the settings flow and
[security requirements](../standards/security-requirements.md) for the
implemented security contract.

## Generated and runtime files

Several local files are outputs, not image source:

| Path | Purpose |
|---|---|
| `.env.test.file`, `.env.production.file` | Protected Compose interpolation generated by the installer |
| `deployment/settings/` | Operator-prepared protected production settings |
| `deployment/apache/*.conf` | Apache configuration rendered before Compose validation |
| `*.bu-isciii-update` | Candidate produced when scaffold synchronization finds managed drift |
| `logs/`, `documents/` | Local runtime data covered by the generated rules |

The default Django `DJANGO_SETTINGS_PATH` is outside the repository. If an
application chooses another location, verify that it is outside Git and the
build context or add an appropriate standard rule.

## When to customize the ignore files

Applications may need exclusions for application-generated files, local
development artifacts, large local data, or framework caches. A new pattern
must not re-include standard-protected settings or runtime files, and it must
not hide source required by the image build.

Both generated ignore files are currently standard-managed and have no
application-owned block. Direct local edits are reported by
`scripts/scaffold.py check` as managed drift. Add a generally reusable rule to
the corresponding template under `scaffold/templates/common/`. If a rule is
application-specific, first add a supported customization mechanism to the
standard rather than relying on an untracked local edit. See the
[scaffold workflow](scaffold-workflow.md) for ownership and drift handling.

## Quick checks

Before committing or building, confirm that:

- real production secrets are not tracked by Git;
- generated Compose and runtime settings are not tracked;
- protected settings are excluded from the build context;
- logs, documents, dependencies, and build output are not copied accidentally;
- required source and explicitly allowed test/template files remain included.

Use `git status --ignored` to inspect Git exclusions. Review the generated
[Git ignore template](../scaffold/templates/common/.gitignore.tmpl) and
[Docker ignore template](../scaffold/templates/common/.dockerignore.tmpl) when
checking exact patterns.
