# Infrastructure requirements

## 1. Purpose and scope

This standard defines the infrastructure that MUST exist before a BU-ISCIII application deployment starts. It applies to standalone and multi-service container deployments generated by this repository.

Application profiles and addons may add requirements. Provider-specific request procedures belong in the
[virtual-machine guide](../guides/requesting-a-virtual-machine.md), using the [infrastructure request template](../templates/infrastructure-request.md).

## 2. Environment and operating system

Each deployment environment MUST have a documented purpose, owner, and
separation from other environments. Production data and credentials MUST NOT be used in a test environment unless an approved exception defines how they are protected.

The deployment host MUST run Linux and provide the commands used by the generated scripts, including Bash and standard filesystem and network tools. The selected operating-system distribution and version MUST be documented and MUST support the selected container engine and Compose provider.

This repository does not prescribe one Linux distribution. The infrastructure owner MUST document the operating-system maintenance owner, update policy, and supported lifetime. An end-of-life operating system MUST NOT be used for a new production deployment.

## 3. Capacity and storage

The deployment MUST document the CPU, memory, and storage assigned to the host.
Sizing MUST account for all selected application services, addons, container image builds, concurrent deployment operations, and expected workload.

Storage planning MUST distinguish:

- operating-system and container-engine storage;
- image and build-cache storage;
- named volumes managed by the container engine;
- host paths exposed through bind mounts;
- application and proxy logs; and
- backup storage.

A bind mount makes a declared host file or directory available inside a container. A named volume stores data in a location managed by Docker or Podman. Capacity, expected growth, performance needs, and the owner of each persistent storage area MUST be documented. Backup capacity MUST be separate from the capacity needed to run the live deployment.

The host MUST have enough free space to build and retain the images required by the deployment without risking loss of persistent data. Any automated cleanup MUST exclude declared persistent data and current recovery material.

## 4. Deployment account and SSH access

Every deployment MUST use an identified service or deployment account. Its owner, groups, home or working directories, and allowed privileges MUST be documented.

The account MUST be able to:

- read the application and deployment repositories;
- execute the selected container engine and Compose provider;
- create or update the declared deployment files and host bind sources; and
- read protected runtime configuration needed by the installer.

The account MUST NOT receive unrestricted privilege solely to avoid correcting path ownership or container-engine configuration. Administrative privilege MAY be used for documented host preparation, such as creating institutional directories, but routine deployment commands SHOULD run without it.

Interactive remote administration MUST use SSH or an institutionally approved equivalent. Authorized people or automation identities, authentication method, source restrictions, privilege-escalation rights, and access-removal owner MUST be documented. Shared personal accounts SHOULD NOT be used.

## 5. Network, DNS, and firewall

Every environment MUST document its network zone and required connectivity.
Firewall rules MUST identify source, destination, protocol, port, and purpose.
Only ports required by the selected topology SHOULD be reachable from outside the host.

Inbound access MUST cover the intended public or institutional entry points and any approved administration endpoints. Databases and internal Compose services SHOULD remain private unless an explicit integration requires otherwise.

Outbound access required for image registries, source repositories, operating- system or language packages, DNS, time synchronization, email, identity providers, external databases, APIs, monitoring, or backup systems MUST be identified before installation. Infrastructure policy MAY provide these services through approved proxies or mirrors.

Every externally addressed service MUST have a documented hostname owner. DNS records, aliases, and the expected resolution scope MUST be agreed before final acceptance. Test and production names MUST be distinguishable.

## 6. Container engine

The host MUST provide either Docker or Podman and a working Compose provider.
The selected engine, version, installation owner, update policy, and Compose command MUST be documented.

Docker deployments use `docker compose`. Docker is not required to run
rootless. The deployment account MUST have the access required by the chosen Docker installation, and the security implications of daemon access MUST be accepted by the infrastructure owner.

Podman deployments use `podman-compose` when installed, otherwise `podman compose`. Rootless Podman SHOULD be used when it is the approved host model. A rootless deployment MUST provide:

- subordinate UID and GID mappings appropriate for the deployment account;
- working user namespaces and `podman unshare`;
- storage on a filesystem supported by rootless Podman;
- a Compose provider available to the same account; and
- a documented mechanism for services that must continue after logout or reboot.

The same account MUST run the installer, Compose provider, and rootless Podman for a given deployment. Rootless Podman storage MUST NOT be edited directly to repair application permissions; the generated permission action operates on declared paths and container mounts.

The engine MUST support the image-build features used by the selected profile.
In particular, a Django production build requires support for the `--secret` build option and Dockerfile
`RUN --mount=type=secret` syntax so configuration can be supplied without copying secrets into image layers.

## 7. SELinux

The infrastructure request MUST record whether SELinux is unavailable,
disabled, permissive, or enforcing. SELinux MUST NOT be disabled merely to make a bind mount work.

On an SELinux host, the infrastructure and deployment owners MUST agree how declared bind mounts receive appropriate labels. Unix ownership and mode do not replace SELinux access control. Any required policy exception or manual label operation MUST name the affected path and be documented in the operator runbook.

## 8. TLS

Every externally exposed production HTTP service MUST have a documented TLS termination point and responsible owner. The certificate names, issuer, installation location, renewal process, expiry monitoring, and handoff between the TLS endpoint and the application or proxy MUST be documented.

TLS MAY terminate in infrastructure outside the generated topology or in a selected proxy addon. The choice MUST match the forwarded protocol and host configuration supplied to the application. Real private keys and certificates MUST remain outside source control and container image layers.

## 9. Logging and monitoring

The application and infrastructure owners MUST agree who operates logging and monitoring. The agreement MUST identify:

- application, proxy, container-engine, and host logs that are retained;
- log destinations, access controls, rotation, and retention;
- health or readiness endpoints that are monitored;
- alert recipients and response ownership; and
- any external metrics or monitoring agents required on the host.

The generated smoke test verifies deployment behavior at install or upgrade time. It does not replace continuous production monitoring.

## 10. Backups and recovery

Every production deployment MUST assign an owner for backup and restore. The backup scope MUST cover all authoritative persistent data required to recover the selected profiles and addons, including external databases, named volumes, host bind sources, and protected configuration where applicable.

The following decisions MUST be documented:

- backup method and schedule;
- retention and storage location;
- access controls appropriate to the data and secrets in the backup;
- recovery-point and recovery-time expectations;
- restore procedure and responsible operator; and
- how and when restore testing is recorded.

A versioned realm import or other bootstrap input does not replace a backup of authoritative runtime data. Backups MUST NOT rely only on storage located on the deployment host when loss of that host is within the recovery scope.

See the [backup and restore guide](../guides/backups-and-restore.md) for the operational procedure.

## 11. Worked example

The following example shows how the requirements can describe one running environment. It is illustrative: its names, sizes, ports, and products are not universal requirements.

| Area                   | Example record                                                                                                                                                                                     |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Environment            | Production deployment of iSkyLIMS on host `dcontainers00`, owned by the application and infrastructure teams                                                                                       |
| Operating system       | Rocky Linux 9, maintained through the institutional operating-system update process                                                                                                                |
| Capacity               | 8 virtual CPU cores, 16 GB RAM, and 200 GB assigned to container images and application data; the sizing record explains the expected workload and growth                                          |
| Deployment account     | `svc-iskylims`, with SSH keys for authorized operators and only the privileges needed to run the selected engine and access declared deployment paths                                              |
| Container engine       | Rootless Podman and its Compose provider, always run as `svc-iskylims`; subordinate UID/GID ranges and persistence across logout/reboot are configured                                             |
| Application storage    | Named volumes hold uploaded documents and static files; declared host binds hold logs and protected settings                                                                                       |
| DNS                    | `iskylims.isciii.es` resolves to the institutional public entry point                                                                                                                              |
| Inbound network        | Clients reach TCP 443 on the institutional Forti appliance; the appliance can reach the application host on the documented backend  Port                                                            |
| TLS                    | The Forti appliance presents the certificate for `iskylims.isciii.es`, terminates HTTPS, and forwards requests to the application or proxy. The certificate owner and renewal process are recorded |
| SELinux                | SELinux is enforcing; declared bind mounts use the generated relabel options, and any additional host labeling is recorded in `LEAME.md`                                                           |
| Logging and monitoring | Container and application logs are retained in the declared location and forwarded to the institutional logging service; the application health URL is monitored                                   |
| Backups                | The database, application volumes, bind-mounted data, and protected configuration have named backup owners, retention, and a tested restore procedure                                              |

### DNS, HTTP, HTTPS, and TLS in this example

DNS maps a name such as `iskylims.isciii.es` to an IP address. DNS alone does
not decide whether the service uses HTTP or HTTPS.

- `http://iskylims.isciii.es` is plain HTTP unless another component redirects
  it.
- `https://iskylims.isciii.es` uses TLS. The client checks the certificate for   that hostname and encrypts the connection.
- In this example, the Forti appliance owns the public TLS endpoint. It may   forward the request to a private HTTP backend or to another HTTPS endpoint, depending on the documented infrastructure design.

The deployment record therefore needs both the DNS owner and the TLS owner. It also needs the certificate renewal responsibility and the network path from the Forti appliance to `dcontainers00`. The generated deployment does not configure the institutional Forti appliance automatically.

## 12. Readiness evidence

Before production installation, the responsible owners MUST record that:

- the host and operating system meet the documented support decision;
- capacity and persistent storage have been allocated;
- the deployment account and remote access work;
- the selected container engine and Compose provider work for that account;
- required DNS and network paths are available;
- SELinux handling has been agreed where applicable;
- TLS ownership and renewal are defined; and
- logging, monitoring, backup, and restore responsibilities are assigned.

Missing infrastructure, unresolved ownership, or an unsupported environment MUST be
corrected or recorded as an approved exception before production acceptance. See
[exceptions and compliance](exceptions-and-compliance.md).
